# cleanroom-writing 技能开发背景与应用说明

## 一、开发背景

在使用大语言模型开展写作时，工作过程通常不是一次完成的。用户与模型会先讨论目标，提出多个方案，比较不同表述，否定不合适的思路，再逐步确定最终内容。这种交互方式有利于形成更成熟的结论，但也带来一个反复出现的问题：已经被否定的方案、只用于内部决策的理由、旧版本措辞以及已经解决的争议，可能在后续成稿时重新进入正文。

例如，讨论过程中曾比较方案A和方案B，最后明确采用方案B。理想的最终文稿应直接陈述方案B，但模型有时会写成“本方案不是采用方案A，而是采用方案B”，或者补充“为避免此前的问题，本方案……”。这样一来，目标读者并不知道的讨论历史被带入正文，已经废弃的概念也因为否定、对比或解释而重新出现。

这种现象并不限于专利写作。在论文、技术报告、规章制度、项目方案、合同说明、产品文案、汇报材料和一般公文中，只要经历了多轮讨论、多个版本或反复修改，都可能发生。我们将其概括为“废案回流”或“决策历史泄漏”。

其根本原因是：大语言模型会把上下文中的内容都视为潜在写作材料。一个方案即使已经被否定，也不会从上下文中真正消失；如果它被反复讨论，反而可能具有更高的显著性。同时，模型天然倾向于用对比和解释来表现逻辑完整性，因此容易使用“不是……而是……”“不再……”“与原方案相比……”“为避免误解……”等结构，把本应只存在于讨论记录中的内容带入最终文本。

## 二、开发动机

`cleanroom-writing` 的开发目的，是在“讨论过程”和“最终交付物”之间建立一道明确的内容边界。

它并不限制讨论阶段提出备选方案、记录失败思路或解释取舍理由。相反，这些内容对于作出可靠决定很重要。该技能要解决的是：讨论材料可以帮助决策，但不能因为出现在上下文中，就自动获得进入最终文稿的资格。

这一技能希望实现以下目标：

1. 将已经确认的最终内容与讨论历史分开管理。
2. 确保后出现的明确决定能够覆盖较早决定。
3. 防止废案通过否定句、对比句、免责声明或补充解释重新进入正文。
4. 防止模型把内部修改理由写成面向目标读者的内容。
5. 保证正文、摘要、示例、表格、图示和附件反映同一个最终状态。
6. 让不了解讨论过程的读者也能独立、自然地理解最终文稿。

## 三、核心工作方式

`cleanroom-writing` 不直接依据全部对话记录起草最终文稿，而是先从讨论和源材料中建立一份“权威状态”。内容被划分为四类：

| 类别 | 含义 | 在最终文稿中的处理 |
|---|---|---|
| 已确认内容 | 最终采用的事实、主张、定义、措辞和结构 | 可以写入 |
| 已确认修改 | 已经确定需要执行的具体改动 | 执行后写入 |
| 排除内容 | 废案、旧措辞、被覆盖的决定和内部理由 | 不得写入，仅用于审计 |
| 未决事项 | 尚未形成结论且会影响结果的问题 | 暂不写入，必要时询问 |

在此基础上，技能提取一份只包含最终有效内容的“纯净执行清单”，并依据该清单起草或修改文稿。完成后再执行独立审计，重点检查：

- 每个实质性陈述是否来自已确认内容或权威源材料；
- 是否残留被后续决定覆盖的定义、数字、方案和措辞；
- 已排除概念是否借助“不再”“不是……而是……”等表达重新出现；
- 是否把内部选择理由或修改过程写入正文；
- 标题、摘要、正文、示例、表格和图示是否保持一致。

这些对比性或否定性表达只是检查信号，并非一律禁止。真实的适用范围、必要限制、安全条件、法律边界，以及目标读者确实需要了解的比较，仍应保留。判断标准不是句子中是否出现“不”字，而是该信息是否服务于最终文稿及其目标读者。

## 四、主要应用场景

该技能特别适用于以下情形：

### 1. 多轮讨论后形成正式文稿

讨论过程中出现过多个版本、备选方案和不同意见，最终需要生成一份只呈现确定结果的文稿。

### 2. 根据修改计划统一修订文件

已经逐条讨论并形成修改决定，需要一次性修改正文、摘要、实施例、表格和图示，同时避免把逐条讨论的理由写进成稿。

### 3. 合并多人或多来源意见

材料中包含作者意见、审阅意见、旧稿、批注和修改记录，需要从中提取当前有效结论，而不是把全部过程性信息混合起来。

### 4. 清理经过反复修改的旧文稿

文稿中已经出现旧概念残留、版本措辞冲突或面向旧争议的解释，需要恢复为一致、独立的最终状态。

### 5. 正式性要求较高的写作

包括专利文件、论文、技术报告、制度文件、合同附件、项目申报书、产品规范和对外说明。这些文稿通常不应暴露无关的内部讨论历史。

## 五、不适合直接调用的情形

以下任务通常不需要或不适合使用该技能：

- 当前仍处于开放式头脑风暴阶段；
- 用户希望保留不同方案的比较过程；
- 文稿本身就是决策记录、修改说明、评审回复或版本变更说明；
- 用户明确要求解释为什么放弃某个方案；
- 尚未形成足以支持最终成稿的明确决定。

在这些场景中，讨论历史本身就是交付内容的一部分，强行清除反而会损失必要信息。

## 六、不能调用 skill 时的两份配套文档

为了在不支持自定义 skill、不能安装 skill，或者只能够通过普通提示词与模型交互的环境中复用同一套方法，我们另外编写了两份独立的 Markdown 文档。二者分别对应“事前预防”和“事后修复”。

### 1. 《LLM写作开始前约定与检查》

文件：[LLM写作开始前约定与检查.md](./LLM写作开始前约定与检查.md)

这份文档用于写作任务开始之前。适用情形是：已经预见到任务将经历多轮讨论、多个备选方案或反复修改，希望从一开始就建立清晰的状态边界。

文档包括：

- 可以直接发送给LLM的“开始前约定”；
- 已确认内容、已确认修改、内部理由、排除内容和未决事项的记录模板；
- 正式写作前检查表；
- 纯净执行清单模板；
- 交付前检查表；
- 适合简短对话场景的精简调用版本。

它的主要作用是预防。通过在任务开始时明确“讨论过不等于确认采用”，并持续维护最终有效状态，降低废案进入成稿的概率。

### 2. 《LLM文稿废案回流检查与修复》

文件：[LLM文稿废案回流检查与修复.md](./LLM文稿废案回流检查与修复.md)

这份文档用于写作开始前没有建立约定，或者现有文稿已经发生废案回流的情况。

文档提供了一套分阶段修复流程：

1. 从讨论记录、修改计划和最新决定中恢复当前有效状态；
2. 根据版本历史、废案否定、内部辩解、决策理由和隐性概念残留等信号定位问题；
3. 逐处判断相关内容对目标读者是否必要；
4. 在用户确认后形成纯净修复清单；
5. 统一修改并检查正文、摘要、表格和图示是否同步。

它强调先检查、后修改，避免模型在没有厘清当前状态时直接重写文稿。同时，它不会机械删除所有否定句，而是根据内容是否服务目标读者作出判断。

## 七、三者之间的关系

三者使用的是同一套原则，但承担不同角色：

| 工具 | 定位 | 适用时间 |
|---|---|---|
| `cleanroom-writing` skill | 可重复执行的完整写作与审计工作流 | 支持调用skill时 |
| 《LLM写作开始前约定与检查》 | 普通提示词环境下的事前预防方案 | 写作开始前 |
| 《LLM文稿废案回流检查与修复》 | 普通提示词环境下的事后诊断与修复方案 | 文稿已经出现问题后 |

如果运行环境支持该 skill，应优先使用 `cleanroom-writing` 完成最终起草或修订。如果不能调用 skill，可在任务开始前使用第一份文档；若没有提前建立约定，或者文本已经受到讨论历史污染，则使用第二份文档进行检查和修复。

## 八、设计原则总结

这套方法的核心不是减少讨论，而是让讨论与成稿各司其职：

> 讨论记录保存“为什么这样决定”，最终有效状态记录“最后决定了什么”，最终文稿只呈现“目标读者需要知道什么”。

当三者被清楚分开时，大语言模型仍然可以充分参与探索、比较和推理，同时又能产出简洁、一致、不携带无关版本历史的正式文本。
